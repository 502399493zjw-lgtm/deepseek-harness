# Agent Note: Codex 共享池开发流程

Status: implemented

[English](2026-08-18-codex-shared-pool-development-flow.md) | 中文

## Problem

项目原先要求每项任务都从托管 worktree 开始，偏好 detached `HEAD`，并且在用户逐项提出之前不允许提交、推送或创建拉取请求。这把隔离机制和交付策略混在了一起。实现完成后可能只剩匿名 worktree 中的一批未提交文件，既没有稳定的评审单元，也没有远端验证和清晰的合并路径。

## Decision

具名任务分支及其拉取请求是开发工作的持久单元。当当前检出属于其他工作、存在妨碍任务的无关改动、需要并行执行，或用户明确要求隔离时，worktree 才提供条件式隔离。detached `HEAD` 不是持久的开发或交接状态。

实现请求授权智能体进行范围内编辑、创建任务分支、提交已审查的路径、推送、创建或更新拉取请求，以及调查或重试 CI。智能体分别报告聚焦的本地证据和精确对应已推送 head 的远端 CI。拉取请求 CI 负责完整检查和平台覆盖；只有用户明确要求、CI 不可用或覆盖不足、需要复现失败，或者变更不可避免地影响整个仓库时，才运行完整本地套件。

合并仍是需要用户单独确认的操作。破坏性历史修改、删除分支或 worktree，以及部署也需要独立授权。依赖用户桌面实时状态的验证只在候选改动已经提交后进行，发现的修复返回同一任务分支。

## Alternatives considered

**每项任务都使用托管 worktree。** 统一隔离很简单，但在干净任务分支已经足够时会增加额外操作，而且隔离本身不会产生可评审结果。

**在用户要求交付前一直保留 detached worktree。** 这避免主动修改远端，但经常让已完成工作缺少稳定名称、提交和 CI 结果。

**每次推送前运行完整仓库套件。** 这会重复 CI、拖慢反馈，并掩盖与改动行为直接对应的聚焦证据。

**CI 通过后自动合并。** 绿色 head 只能证明检查通过，不能证明用户接受范围、取舍或合并时机。

## Consequences

实现任务通常以具名分支上的已审查提交、已推送的拉取请求和明确的 CI 状态结束，然后等待用户明确确认合并。worktree 的使用由实际证据决定，而不是固定仪式。智能体获得完成评审闭环的权限，同时合并和破坏性操作仍保留清晰的人工检查点。
