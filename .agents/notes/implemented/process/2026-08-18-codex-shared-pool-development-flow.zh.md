# Agent Note: Codex 共享池开发与交付流程

Status: implemented

[English](2026-08-18-codex-shared-pool-development-flow.md) | 中文

## Problem

项目原先把隔离机制与交付策略混在了一起：每项任务都从托管 worktree 开始，偏好 detached `HEAD`，并且在用户逐项提出之前不允许提交、推送或创建拉取请求。实现完成后可能只剩匿名 worktree 中的一批未提交文件，既没有稳定的评审单元，也没有远端验证。

替代流程又在拉取请求合并处停止，并把之后的活动统称为部署。这仍然掩盖了多个独立结果。合并只更新 Git 历史，不会重新构建源码检出、替换正在运行的 DSH 进程、更新已安装的 profile 依赖、生成经过验证的 tarball，也不会发布 npm 包。它还把验证对象写成实时桌面应用，但这个组合包运行在 DSH 中；Codex Desktop 不是它的应用宿主。

## Decision

### 一个持久的开发单元

具名任务分支及其拉取请求是开发工作的持久单元。当当前检出属于其他工作、存在妨碍任务的无关改动、需要并行执行，或用户要求隔离时，worktree 才提供条件式隔离。detached `HEAD` 不是持久的开发或交接状态。

实现请求授权范围内编辑、创建分支、提交已审查的改动、推送、创建或更新拉取请求，以及调查 CI。聚焦的本地证据与精确对应已推送 head 的 CI 分别报告。拉取请求 CI 负责完整检查和平台覆盖；只有用户明确要求、CI 不可用或覆盖不足、需要复现失败，或者变更不可避免地影响整个仓库时，才运行完整本地套件。

### 五个交付状态

每次交接都记录每个适用状态：

| 状态 | 必需证据 |
|---|---|
| 代码完成 | 范围内改动与聚焦本地检查位于具名任务分支。 |
| GitHub 已集成 | 已审查的拉取请求合并进明确说明的目标仓库和基础分支。 |
| 本机已应用 | 目标 DSH 安装或源码链接 profile 在重启后运行重新构建的已合并产物，并已验证受影响流程。 |
| 产物可分发 | 一套版本一致的 DSH release-family tarball 已构建并通过安装验证。 |
| 已发布 | 带标签的 release family 已由受保护工作流上传，registry 状态已验证，消费者可以升级。 |

这些状态是相互独立的证据字段，不是一条自动推进的阶梯。拉取请求 CI 可以在合并前验证产物，已发布版本也可能尚未应用到某台机器。合并到个人 fork 不等于合并到上游。合并到任何仓库都不会自动在本机应用结果或完成发布。

### 本机应用

只有收到明确的本机应用请求，才更新本地运行的 DSH 实例。开发期间的测试或分支预览仍属于代码完成的证据，不能据此声称稳定的本机实例已经更新。对于源码链接 profile，操作者把链接的检出更新到预期的已合并提交；manifest 或 lockfile 变化时安装依赖；运行 `pnpm run build`；重启 DSH；刷新浏览器；验证受影响行为。源码启动器不会自行构建，过期的 Host、Client 或前端产物可能继续运行；这遵循[不使用托管安装器的源码运行](../simplification/2026-08-10-source-run-without-managed-installer.md)和 [CLI 源码执行参考](../../../../apps/cli/reference/README.md#source-execution)。

对于通过 npm 或 tarball 安装的 profile，操作者通过 `dsh plugin` 更新 profile 依赖或安装已批准的 tarball，然后重启 DSH 并验证。Git 操作成功从来不能证明其中任一运行路径已经变化。

### 分发

通过 Git 托管地址安装不是这个组合包支持的分发路径。Git 依赖拿到的是源码，需要自包含的 `prepare` 脚本；这个包没有该脚本，并且依赖同一 monorepo 中的兄弟包。

内部共享的 release candidate 是完整且版本一致的 DSH release-family tarball 集合，而不是单独的组合包 tarball。仓库构建整个 family，使用 `pnpm run release:pack --family dsh` 打包，并验证产物集合的安装。这保留了统一版本及 workspace 依赖范围。

公开发布遵循[三条独立序列完成私有 npm 发布](2026-08-10-npm-release-sequences.md)。发布负责人让发布分支与所需上游基线对齐，递增 DSH family 的统一版本，合入已审查的发布改动，创建 `dsh-v<version>`，并从该标签手动触发启用发布的 `Release (dsh)`。受保护的 `npm-publish` environment 与 `NPM_TOKEN` 授权上传。工作流发布已经验证的同一批产物；随后验证 registry，消费者再更新版本一致的 package family 并重启 DSH。

### 权限检查点

合并、破坏性历史修改、删除分支或 worktree、本机应用、修改发布版本、创建标签和发布都是需要分别授权的操作。绿色检查不会授权其中任何一项。尤其不能让合并静默触发服务重启或 registry 写入。

## Alternatives considered

**每项任务都使用托管 worktree。** 当干净任务分支已经足够时，统一隔离会增加额外操作，而且隔离本身不会产生可评审结果。

**把拉取请求合并视为所有请求的完成。** 只有在目标就是源码集成时才成立。对于本机更新或发布请求，这会丢失必要的重新构建、重启、产物和 registry 证据。

**合并后自动更新本机实例或发布。** 这会让 GitHub 决策在缺少独立范围和恢复检查点的情况下修改运行中服务或共享 registry。

**直接分发 GitHub 仓库。** 这个 monorepo 包不能作为自包含 Git 依赖完成构建，profile 安装后会缺少 workspace 产物。

**只共享组合包 tarball。** DSH 各包属于统一版本和内部依赖范围一致的一个 release family；单个未经集合验证的 tarball 不能证明消费者可以解析并运行该集合。

**每次推送前运行完整仓库套件。** 这会重复 CI、拖慢反馈，并掩盖与改动行为直接对应的聚焦证据。

## Consequences

实现任务通常以已审查的拉取请求和明确的 CI 状态结束，然后等待用户确认合并。本机应用请求会继续到重新构建、重启和行为验证。发布请求则根据范围继续到经过验证的 family 产物或受保护的公开发布。

交接不能再只写“完成”或“已合并”。它必须说明仓库与基础分支、每个适用的交付状态、精确的检查或产物验证，以及尚未执行的操作。除非未来产品要求明确引入 Codex Desktop 集成，否则开发流程不再把它作为验证对象。
